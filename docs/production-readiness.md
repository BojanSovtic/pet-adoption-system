# Production readiness

_Assessed 2026-10-26 against the code at `38aaa79` plus the uncommitted Batch A work._

The project is meant to be deployed and used by real people, so "production-ready" is a requirement here, not a nice-to-have. This document lists what is verified, what blocks a public launch, and what can follow.

**Evidence levels:**

- **Tested:** an automated test checks it.
- **Code:** read in the code, but no test.
- **Probed:** observed against the running dev API.

## 2. Launch blockers (P0)

These must be done before real users sign up. They are ordered by risk and dependency.

| #         | Gap (evidence)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | Change                                                                                                                                                                                                                                                                                                                                                                                                       | Acceptance criteria                                                                                                                                            |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **P0-1**  | **Vulnerable dependencies in shipped code** (`pnpm audit --prod`, 2026-10-26). API: `proxy-addr` **critical** (IP spoofing, which matters for the IP-based rate limits behind a proxy), `body-parser` / `multer` / `zod` high (DoS), `qs` / `ip-address` moderate. Web: `react-router-dom` 6.30.3 moderate (open redirect / XSS). Also, `shadcn` (a CLI) is in runtime `dependencies` and adds 20+ advisories.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | Upgrade `express`, `multer`, `zod` and `react-router-dom` (6.30.6+ or 7.x) to patched versions; move `shadcn` to `devDependencies`; add an audit step to CI that fails on high/critical advisories in production dependencies.                                                                                                                                                                               | `pnpm audit --prod` shows no high or critical advisories for API or web runtime packages; CI enforces it; the full test suite and E2E pass.                    |
| **P0-2**  | **Photos are stored byte-for-byte** (`storage.save(key, data)` with the uploaded buffer). EXIF, including **GPS location** from phone photos, is published. Valid magic bytes don't prove a valid image, and there is no size or dimension normalization.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | Re-encode every upload server-side (`sharp`: rotate from EXIF, strip metadata, cap dimensions at ~2000 px, write WebP/JPEG). A file that doesn't decode is rejected (`UNSUPPORTED_IMAGE_TYPE`).                                                                                                                                                                                                              | API test: a JPEG with GPS EXIF is stored without EXIF; an oversized image is downscaled; a "JPEG" with valid magic bytes but garbage after them is rejected.   |
| **P0-3**  | **API error and header gaps** (probed): a body over 100 kB returns **500** and is logged as an unexpected error; unknown `/api/*` routes return Express's **HTML** 404; no security headers; `X-Powered-By: Express`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | Map body-parser errors (413, 415, …) to `ApiErrorResponse`; add a JSON 404 for `/api`; `app.disable('x-powered-by')`; add security headers (`helmet` with a JSON-API config, or a small explicit middleware).                                                                                                                                                                                                | API tests for 413, JSON 404 and the headers. No 5xx for client errors.                                                                                         |
| **P0-4**  | **No production deployment configuration.** Compose is development only (`NODE_ENV: development`); `trust proxy` is hard-coded to 1; nginx sends no security headers (CSP, `frame-ancestors`, `Referrer-Policy`, `nosniff`) and no compression; there's no production `Secure`-cookie test.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | A production config: `NODE_ENV=production`, `TRUST_PROXY` from env, TLS at the proxy with HSTS, nginx security headers + CSP that fits the built app, gzip/brotli. A staging deploy as a rehearsal. **Depends on the hosting decision (D1).**                                                                                                                                                                | A staging URL passes: cookies are `Secure; HttpOnly; SameSite=Lax`; securityheaders.com grade A; no mixed content; the E2E smoke suite passes against staging. |
| **P0-5**  | **No observability.** `console.log` only; no request logging, request ids or structured logs; `/api/health` doesn't check the database; no error tracking. `deployment.md` lists this as "not covered".                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | Structured logs (`pino`) with a request id, method, path, status and duration; no secrets or PII (no bodies, no emails). A request id on 500 responses. `/api/health` (liveness) and `/api/ready` (MongoDB ping). Error tracking optional (D3).                                                                                                                                                              | A request id appears in the logs and in a 500 response; readiness fails while MongoDB is down (test); a log review finds no passwords, emails or cookies.      |
| **P0-6**  | **No backup and recovery.** Nothing documented or automated for MongoDB or the photo storage.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | Backups that match the hosting (managed snapshots or scheduled `mongodump` + photo storage backup), retention, and a **tested restore** procedure in `deployment.md`. **Depends on D1.**                                                                                                                                                                                                                     | A restore drill on staging rebuilds the data and photos from a backup; documented RPO/RTO.                                                                     |
| **P0-7**  | **Account lifecycle and legal basics are missing**: no password reset (a locked-out user can't recover), no account deletion or data export, no privacy notice. Applicant emails are shown to pet owners (by design), but users aren't told on the form.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | Password reset by email (single-use, expiring, hashed token; sessions revoked on reset); account deletion (with a defined effect on pets and applications); a privacy notice and terms page; a note on the apply form that the owner will see your name and email. **Email delivery depends on D2.**                                                                                                         | API tests for the token flow (expiry, single use, revocation); E2E for reset; deletion removes or anonymizes personal data as documented.                      |
| **P0-8**  | **Abuse limits only cover authentication.** Applications, pet creation and uploads are unlimited per user; limits live in process memory (reset on restart, wrong with more than one instance).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Per-user limits on writes (applications, pets, photo uploads). Keep the memory store for a single instance, and use a shared store (MongoDB or Redis) if D1 means several instances.                                                                                                                                                                                                                         | Tests: the Nth create in a window gets 429 `RATE_LIMITED`; limits are documented in `requirements.md`.                                                         |
| **P0-9**  | **A render error blanks the whole app**: no React error boundary or route `errorElement`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | A route-level `errorElement` with a translated "Something went wrong" page and a reload action; report to logging/error tracking (P0-5).                                                                                                                                                                                                                                                                     | Web test: a throwing route shows the error page, not a blank screen.                                                                                           |
| **P0-10** | **Unreliable tests can't gate a release.** API: a two-user test can exceed the 5 s timeout because every sign-up runs a real Argon2 hash (~200 ms alone, 1.3 s for 8 at once on 4 cores) while `nx run-many` runs suites in parallel. A timed-out sign-up then causes a 409 in the next test. With `--parallel=1` the same API suite passed 244/244 at the default timeouts. E2E: two full runs on 2026-10-26 each had one failure, and both times it was **the first scheduled test** (adoption, then registration: `toHaveURL` after sign-up). E2E runs against the **Vite dev server**, so the first page load compiles modules on demand. Test 1 took 15–22 s against 3–8 s for later ones, and repeated runs (`--repeat-each=3`) passed 9/9. The likely cause is cold compile plus an Argon2 sign-up under load, against a 5 s assertion timeout. No trace was kept to prove it. E2E doesn't run in CI. | Cheaper Argon2 parameters in tests only (`NODE_ENV=test`, explicit and tested so production can't use them); keep the 5 s timeout. Run E2E against the **production build** (`vite build` + `vite preview --strictPort`) instead of the dev server, which is faster and closer to production. Playwright: keep traces/screenshots on failure in a stable folder and upload them in CI. Add an E2E job to CI. | 10 consecutive green CI runs of the full suite plus E2E; a deliberately failing E2E test leaves a trace artifact.                                              |

## 4. Decisions needed

- **D1, hosting:** single VM with Docker Compose, or managed services (e.g. MongoDB Atlas + a container platform + object storage for photos)? This sets backups, TLS, `trust proxy`, the rate-limit store and photo storage.
- **D2, email provider** (e.g. Postmark, SES, Resend), for password reset and notifications.
- **D3, error tracking** (e.g. Sentry) or logs only.
- **D4, legal:** the operator identity and contact for the privacy notice; data retention for applications and deleted accounts.

## 5. Suggested order

1. **P0-10** (reliable tests): every later change needs a trustworthy gate. Small.
2. **P0-1** (dependencies), **P0-3** (API errors/headers), **P0-9** (error boundary): small, no external decisions.
3. **P0-2** (image re-encoding): privacy, no external decisions.
4. **P0-8** (write limits), then **P0-5** (logging/health).
5. With D1–D4 decided: **P0-4** (deployment), **P0-6** (backups), **P0-7** (account lifecycle), then a staging rehearsal and launch.
6. P1 items, including Batch B and the admin area, alongside or after launch.
